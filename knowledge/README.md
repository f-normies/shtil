# knowledge/

Клиническое содержание «Клинического компаса» в виде данных: источники, шкалы, правила алертов и маршрутизации, сценарии, синтетические истории болезни. Код приложения исполняет эти данные. Форматы и проверки описаны в [спеке](../docs/superpowers/specs/2026-10-17-knowledge-skeleton-design.md).

Любая правка здесь — только через PR с ревью второго медика (`.github/CODEOWNERS`). Ревьюера указываем сами: `gh pr create --reviewer <логин>`. В приватном репозитории GitHub по CODEOWNERS его не подставляет. Реальных данных пациентов здесь нет и быть не может.

## Проверка

```bash
make knowledge-check      # схемы, ссылки на источники, пороги, табличные тесты правил
make test SCOPE=knowledge # то же плюс тесты самого пакета
```

Проверка печатает все ошибки сразу: `<файл>: <путь до поля>: <что не так>`. Эти же проверки идут в CI. PR с ошибкой не пройдёт.

Готовые примеры каждого формата лежат в `tests/fixtures/valid/`. Это выдуманные данные: копируйте структуру, содержание берите из источников.

Файлы — в кодировке UTF-8. Один ключ в одном блоке YAML пишется один раз: повтор считается ошибкой. В `scales/`, `rules/` и `scenarios/` лежат только файлы `<id>.yaml`, в `cases/` — только каталоги историй.

## Статус

Поле `status` есть у шкал, правил, сценариев, видов признаков риска и препаратов. У групп препаратов статуса нет: они действуют через правила препарата.

- `draft` — черновик, приложение его не использует.
- `reviewed` — проверено вторым медиком; ставится в PR с ревью.

## Источник → `sources/manifest.yaml`

Файл обязателен, даже если источников пока нет: `sources: []`.

```yaml
sources:
  - id: kr-depression-2024          # латиница, цифры, дефис
    title: "Депрессивный эпизод, Рекуррентное депрессивное расстройство"
    kind: clinical_guideline        # clinical_guideline | drug_label | patient_leaflet | scale_validation | drug_registry | other
    publisher: "Общественная организация «Российское общество психиатров»; одобрены научно-практическим советом Минздрава России"
    url: https://cr.minzdrav.gov.ru/view-cr/301_3
    version: "301_3"
    date: 2024-08-26                # дата размещения версии в рубрикаторе
    license: "открытый доступ в рубрикаторе КР Минздрава России; условия копирования не указаны, храним только ссылку"
    file: null                      # копия в sources/files/ или null, если хранить нельзя
    supplementary: false            # true — международный источник, только как дополнение (kind: other)
    icd10: [F32, F33]               # только у clinical_guideline: коды, рубрики или диапазоны МКБ-10
```

`icd10` — коды МКБ-10, которые покрывает клиническая рекомендация: код (`F41.1`), рубрика (`F32` покрывает `F32.1`) или диапазон (`F30-F39`). У `clinical_guideline` поле обязательно и не пустое, у других видов источников его нет. По нему раздел «Терапия» выбирает КР к активным диагнозам пациента (спека #107). Сопоставление кодов — решение медика, его проверяет ревью.

`drug_label` — инструкция по медицинскому применению или ОХЛП: на неё ссылается `label` препарата, её индексирует база знаний для врача. `patient_leaflet` — листок-вкладыш для пациента. Он годится как дополнительная ссылка в сценарии, но `label` препарата на него не указывает, и в базу знаний врача он не попадает.

Ссылка на источник везде одинаковая: `{source: <id>, locator: "раздел 3.1, с. 24"}`. По `locator` проверяющий находит место в документе.

Копия документа лежит в `sources/files/`, в `file` пишется путь вида `files/<имя>`. Международный источник (`supplementary: true`) служит только дополнением. У правила, у валидации шкалы и у порога должен быть хотя бы один основной источник.

## Шкала → `scales/<id>.yaml`

Имя файла совпадает с `id`. Балл за ответ пишется прямо в `value` варианта, обратного подсчёта нет. `scores` — одна или несколько сумм (у HADS две). Пороги `bands` должны без пропусков и наложений покрывать диапазон суммы и не выходить за него. `id` пунктов и сумм не повторяются и не совпадают между собой. В `validation` нужна ссылка на публикацию о валидации русскоязычной версии (`kind: scale_validation`). У шкалы, которую заполняет врач (`respondent: clinician`), вместо неё подойдёт приложение КР Минздрава с русским текстом шкалы (`kind: clinical_guideline`). Шкала без подходящей лицензии (`license.allowed: false`) хранится только со `status: draft` и не используется. Пример: `tests/fixtures/valid/scales/example-mood.yaml`.

Когда по шкале уже есть результаты пациентов, любая правка её определения — это новая версия: увеличьте `version` на 1. Без этого приложение не сможет сравнить старые ответы с новыми.

## Правило → `rules/<id>.yaml`

- `kind: alert` — критическое состояние, экстренное оповещение врача; уровень всегда `mandatory`.
- `kind: routing` — направление к психиатру; `level: mandatory` («обязательно») или `desirable` («желательно»).
- `when` — дерево из `any:` / `all:` и сравнений `{scale, item | score, op, value}`; `op` — `>=`, `>`, `<=`, `<`, `==`. Если у сравнения нет данных (шкала не заполнена), оно ложно.
- `cases` — табличные тесты: `given` (ответы и баллы), `fires` (сработает ли), `source`. Нужен хотя бы один случай с `fires: true` и один с `fires: false`. В `given` — только шкалы, пункты и суммы, которые существуют.

Пример: `tests/fixtures/valid/rules/`.

## Решения по сигналам → `signal-decisions.yaml`

Как врач закрывает сигнал ([спека #93](../docs/superpowers/specs/2026-10-21-93-signal-decisions-design.md), [спека #95](../docs/superpowers/specs/2026-10-22-95-alert-decisions-design.md)). Один файл с `version`, `status` и четырьмя разделами:

- `safety` — сигналы о суицидальном риске (правила `kind: alert` и виды признаков `signs/`). `decisions` — решения, которые закрывают сигнал: `id`, `text`, `reason_hint` (что врач пишет в причине), `sources`. `no_contact` — запись «Не удалось связаться»: пишется в историю, сигнал не закрывает. Источник обязателен и должен быть основным. Варианта «отклонить» нет.
- `therapy` — сигналы безопасности терапии (#29). `decisions`: `id`, `text`, `reason_hint`, `applies_to` — виды сигнала (`contraindication`, `caution`, `reaction`), `sources`. На каждый вид нужен хотя бы один вариант. Организационный вариант может быть без источника; если источники есть, нужен основной.
- `referral_decline` — причины отказа от направления к психиатру. Нужна причина `other` («Другое»). У организационной причины источника может не быть. Комментарий врача обязателен при любой причине.
- `snooze` — отсрочка «Желательно»: предел `max_days`, готовые варианты `presets_days` строго по возрастанию и не больше предела, обоснование `basis`.

Загрузчик без этого файла не падает: в мини-каталогах `knowledge/` тестов API он не нужен. В репозитории его наличие и статус `reviewed` проверяет `tests/test_repository_signal_decisions.py`. Пример: `tests/fixtures/valid/signal-decisions.yaml`.

## Расписание опросов → `scale-schedule.yaml`

Когда пациенту положен опрос и когда врач видит пропуск ([спека #111](../docs/superpowers/specs/2026-10-21-111-scale-schedule-design.md)). Поля: `version`, `status`, `grace_days` (через сколько дней после планового дня без ответа — пропуск), `grace_basis` (обоснование срока), `allowed_period_days` и `allowed_period_basis` (из каких периодов врач выбирает частоту опроса своего пациента и почему, [спека #180](../docs/superpowers/specs/2026-10-29-180-personal-scales-design.md)), `scales` — шкалы с `scale`, `period_days` и `source`. Первый опрос — в день регистрации, следующий — через `period_days` после ответа. Правило целиком — в спеке.

Проверки: шкала есть и её заполняет пациент, повторов нет, `period_days` и каждый допустимый период больше `grace_days`, `period_days` входит в `allowed_period_days`, источник есть в манифесте и он основной. Загрузчик без файла не падает; наличие и статус `reviewed` в репозитории проверяет `tests/test_repository_scale_schedule.py`. Пример: `tests/fixtures/valid/scale-schedule.yaml`.

## Экран помощи пациенту → `patient-help.yaml`

Что видит пациент в опасности ([спека #57](../docs/superpowers/specs/2026-10-25-57-patient-help-screen-design.md)): `title`, `text` с `sources`, номера `contacts` и дата проверки `checked_on`. У контакта `id`, `number` (только цифры: из него строится ссылка `tel:`), `label` — подпись кнопки, `primary` — главная кнопка (ровно одна), `sources`. Источники обязательны, нужен основной. Дата проверки не позже сегодняшней. Фразы о враче здесь не пишутся: это состояние системы, они в коде PWA.

Экран открывается по правилам `kind: alert`, отдельного порога в файле нет. Загрузчик без файла не падает, в репозитории его проверяет `tests/test_repository_patient_help.py`. Пример: `tests/fixtures/valid/patient-help.yaml`.

## Вид признака риска → `signs/<id>.yaml`

Признаки риска, которые LLM ищет в дневнике и чате пациента ([спека #32](../docs/superpowers/specs/2026-10-17-32-freetext-analysis-design.md), раздел 6). Модель решает только, есть ли признак этого вида в тексте. Заголовок сигнала (`title`) и действия врача (`doctor_actions`) берутся из файла, у них должен быть основной источник.

- `definition` — что считается признаком, с примерами формулировок и тем, что признаком не считается. Текст подставляется в промпт. Правка определения меняет версию промпта.
- `rank` — тяжесть, 1 — самый тяжёлый. Если в тексте несколько видов, заголовок сигнала берётся у самого тяжёлого. Более тяжёлый вид всегда даёт новый сигнал врачу. У видов `reviewed` ранги не повторяются.

Без хотя бы одного вида `reviewed` `worker` не стартует: иначе проверка риска молча ничего бы не находила. Пример: `tests/fixtures/valid/signs/`.

## Снимок ГРЛС → `sources/files/grls.csv`

По снимку сверяются названия препаратов из текста пациента. Колонки: номер регистрационного удостоверения, торговое наименование, МНН, статус (`active`, `suspended`, `inactive`, `unknown` — номер есть только в истории изменений). Руками не правится. Обновление:

```bash
uv run --package clin-compass-knowledge --directory knowledge python -m clin_compass_knowledge grls-update
```

Команда берёт свежую выгрузку со страницы поиска ГРЛС, пересобирает снимок и ставит дату выгрузки в запись `grls` манифеста. Результат — PR с ревью медика.

## Препарат → `drugs/<id>.yaml`

Справочник, по которому `therapy` проверяет и предлагает назначение ([спека #28](../docs/superpowers/specs/2026-10-18-28-therapy-design.md), раздел 4). Данные — по инструкции (`label`, источник вида `drug_label`), у каждого поля ссылка на раздел.

- `registration` — номер РУ и снимок реестра (`drug_registry` с файлом). Проверка требует, чтобы номер был в снимке со статусом `active`.
- `indications` — показания с кодами МКБ-10. Коды сопоставляет медик: в инструкции их нет. `requires_any` — ещё один нужный код (например, U09.9 для состояния после COVID-19). `manual` — условия, которые подтверждает врач.
- `regimen` — схема по инструкции: форма из `forms`, разовая доза, кратность, расписание, длительность (`days` и `max_days` для курса, без них длительность определяет врач). Отклонение от схемы — назначение вне инструкции.
- `contraindications` и `cautions` — правила безопасности ([спека #29](../docs/superpowers/specs/2026-10-18-29-therapy-safety-design.md)): противопоказание убирает препарат из предложений, мера предосторожности даёт предупреждение «желательно». Условие — одно из: `diagnosis` (коды, рубрики, диапазоны `F00-F09` и `K74.3-K74.6` с границами одной точности; код пациента входит в шаблон, если начинается с него: `K70.30` — в `K70.3`), `fact` (`egfr`, `child_pugh`, `pregnant`, `breastfeeding`), `medication` (группа из `drug-groups/`, `within_days` — сколько дней после отмены условие ещё действует, последний день включительно), `ask` (вопрос, который всегда решает врач). Неизвестное значение даёт `unknown`: врач видит, что уточнить. У правила есть табличные случаи `cases` с `result: yes|no|unknown`; проверка их исполняет и требует случаи «да» и «нет». Правило с вопросом `ask` никогда не даёт «нет», поэтому ему нужны случаи «да» и `unknown`.
- `adverse_reactions` — нежелательные реакции из инструкции: `level` — уровень сигнала, если реакцию отметил пациент; `patient_reportable` и `patient_title` — может ли пациент её отметить и как она называется простыми словами.
- `reaction_actions` — действия врача по отметке реакции пациентом, с `sources`. Обязательно, если у препарата есть реакции `patient_reportable`.
- `additional_monitoring` — препарат подлежит дополнительному мониторингу: в черновике извещения о нежелательной реакции ставится пометка ▼.
- `version` — целое; растёт при изменении правил.

## Группа препаратов → `drug-groups/<id>.yaml`

Состав группы для условий `medication`: МНН в начальной форме, как в снимке ГРЛС. Перечни в инструкциях часто даны примерами, поэтому состав — решение медика с источником. Тест `test_repository_drugs.py` сверяет каждый МНН группы со снимком: опечатка дала бы молчаливый `pass`.

Комбинированный МНН препарата пациента делится на действующие вещества по «+», «;» и « и », квадратные скобки снимаются. Вещество совпадает с членом группы целиком или начинается с него целым словом: «фенобарбитал» находит «фенобарбитал натрия», а «зверобоя трава» не находит «зверобоя травы экстракт» — такое написание добавляется в группу отдельно.

Пример: `tests/fixtures/valid/drugs/example-drug.yaml`.

## Сценарий → `scenarios/<id>.yaml`

Профиль синтетического пациента и шаги: кто действует (`doctor`, `patient`, `system`), что делает, что ожидаем от системы. `id` шагов не повторяются. У шага системы и у шага со ссылками на шкалы или правила (`refs`) должен быть источник. Пример: `tests/fixtures/valid/scenarios/example-scenario.yaml`.

## История болезни → `cases/<id>/`

- `history.md` — текст синтетической истории.
- `meta.yaml` — признаки шаблона: порядок разделов, детализация (`brief` | `standard` | `detailed`), стиль, формат диагнозов.
- `expected.json` — эталон извлечения: `diagnoses`, `medications`, `risk_factors`, `anamnesis`. Каждое поле — список отдельных фактов. По каждому полю считаются точность (доля верных среди извлечённых) и полнота (доля найденных среди эталонных).

Пример: `tests/fixtures/valid/cases/case-01/`.

### Правила разметки `expected.json`

В эталон попадает только то, что прямо сказано в тексте. Один факт — один элемент списка. Файл оформляем как `cases/case-01/expected.json`: отступ два пробела, каждый элемент списка на своей строке.

**`diagnoses`** — код МКБ-10 (`F32.1`) и текст диагноза. Если кода в тексте нет, его проставляет медик и отмечает это в `diagnosis_format` файла `meta.yaml`. Состояние из строки диагноза, которое не является болезнью, тоже входит в `diagnoses` с кодом рубрики Z: «Лактация» — `Z39.1`.

**`medications`** — один препарат, одна запись по последнему назначению. Прежняя схема приёма, если она важна, идёт в `anamnesis`.

- `name` — русское название, как в ГРЛС: МНН или торговое. Если в тексте латиница (`Sertralini`), пишем `сертралин`.
- `dose` — разовая доза: число и единица по-русски (`0,5 мг`). Если в тексте только суточная доза, пишем `100 мг/сут`.
- `regimen` — кратность, время приёма, связь с едой, «по требованию» или «при …». Сокращения раскрываем: «2 р/д» → `2 раза в день`. Длительность курса сюда не пишем.
- `status` — `current` (текущее назначение) или `past` (прошлый приём).
- `null` — если дозы или режима в тексте нет.

**`risk_factors` и `anamnesis`** — факты вида `{"fact": "живёт один", "quote": "живёт один"}`. `fact` — короткая формулировка без домыслов. `quote` — дословный фрагмент `history.md`. По цитате eval сопоставляет факт с ответом модели. `make knowledge-check` проверяет, что цитата есть в тексте. Сравнение идёт целыми словами. Регистр, лишние пробелы, разница «ё» и «е», кавычки и знаки препинания по краям цитаты не учитываются.

Факторы риска (`risk_factors`):

- суицидальные мысли, намерения и попытки;
- косвенные признаки пассивных суицидальных мыслей: мысли о бессмысленности жизни, отказ от еды, слова о том, что жить или лечиться незачем. Снижение аппетита — жалоба, оно идёт в анамнез;
- ненулевой ответ на пункт шкалы о суицидальных мыслях (пункт 9 PHQ-9);
- самоповреждения;
- употребление алкоголя, табака и ПАВ в любом количестве, даже редкое. Частоту и количество пишем в `fact`. Злоупотребление в прошлом — тоже фактор риска. Полный отказ сейчас («алкоголь не употребляет», «не курит», «не пьёт 8 месяцев») идёт в анамнез;
- приём психотропных препаратов без назначения;
- психические расстройства у родственников;
- одинокое проживание и социальная изоляция, в том числе самоизоляция: «почти перестала выходить из дома», «перестал встречаться с друзьями». Избегание конкретного места из-за страха («избегает метро») — жалоба, она идёт в анамнез;
- текущие стрессовые события: утрата, развод, болезнь близкого, конфликт, потеря работы, выход на пенсию.

Демография, профессия и рабочая нагрузка сами по себе фактором риска не считаются.

Анамнез (`anamnesis`):

- прошлые эпизоды;
- прошлое лечение и его исход, в том числе повторные курсы и длительность курса;
- длительность текущего эпизода;
- жалобы текущего эпизода;
- значимые соматические сведения, которых нет в диагнозах;
- результаты обследований: баллы шкал и их пунктов, анализы, инструментальные исследования, заключения консультантов, числа при осмотре (АД, ЧСС, ИМТ). Ненулевой ответ на пункт о суицидальных мыслях идёт в `risk_factors`;
- отрицательные факты о суицидальных мыслях, алкоголе, табаке и ПАВ: «суицидальных мыслей нет», «алкоголь не употребляет». Их пишем всегда, когда они есть в тексте.

Таблицу размечаем построчно: каждая строка, которая входит в эталон, — отдельный факт. В таблице шкалы это все пункты, в том числе пункты с 0 баллов, и сумма (`case-17`).

Описание статуса при осмотре без чисел в эталон не входит: «тревожна», «тоны ритмичные», «без очаговой симптоматики». Из статуса берём только факторы риска и отрицательные факты о суицидальных мыслях.
